# 从 0 到 1 跑通 Claude Code，省下的时间比你想象的多

事情是这样的。

上周我在折腾一个项目，从零开始搭一个微信公众号的自动发布系统。正常来说这种活儿我得花三四天，写接口、调 bug、处理图片上传，一堆琐碎的东西。

结果这次，从开箱到跑通，一个下午。。。

不是因为我突然变强了。是因为我终于认真用了一个东西，叫 Claude Code。

你可能听过这个名字。Anthropic 出品的，在终端里跑的 AI 编程工具。GitHub 上 11 万颗星。但我猜很多人跟我一样，听归听，一直没真的去试。

直到那天我实在被一堆重复性的编码工作搞烦了，想着，要不试试看？

这一试，确实被震到了。

说实话，我之前对 AI 编程工具是有偏见的。试过不少，Copilot 啊 Cursor 啊，都还行，但总觉得差一口气。补全代码没问题，真要让它干点复杂的活儿就露馅了。要么就是绑在一个笨重的 IDE 里，整个工作流被锁死了。

Claude Code 不一样的地方在于，它直接住在你终端里。

你想想看。你不用换编辑器，不用改工作流，就在你天天敲命令的那个黑框框里，直接跟它说人话就行。「帮我看看这个报错什么原因」「把这坨代码重构一下」「给这个项目写个单元测试」，它就真的动手去做。不是给你提建议然后等你自己改，是直接改文件、跑命令、建 commit。

怎么说呢。

就像你旁边突然坐了一个特别靠谱的同事。你跟他说一声他就去干了，干完还告诉你改了哪里。而且他读了你整个项目的所有代码，比你还要熟。

说到这块，我想先纠正一个很多人对 Claude Code 的误解。

很多人觉得它就是一个聊天机器人，只不过换了个壳放在终端里。其实完全不是。它是一个真正的 agent，能自己决策、自己行动。它不用提前建索引，不用预处理你的项目，就是在你提问的那一刻，动态地探索你的代码库，用 glob 和 grep 搜索，像你自己会做的那样，一步一步地建立理解。

有人打了这么个比方，我觉着特别精准。说 Claude Code 的上下文就像牛奶，新鲜的才好喝。

随着对话越来越长，它对代码的理解会慢慢「变质」。所以遇到复杂任务的时候，别在一个对话里死磕。用 /clear 清掉上下文重新来，或者干脆开一个新对话。听起来有点反直觉对吧，你可能会想「它不是能记住吗」。对，它能记住，但记住的东西太多太杂之后，反而会影响它的判断。

这个经验是我在踩了很多坑之后才悟出来的。

好，回到正题。举几个我自己实际用到的场景。

第一个，理解陌生项目。我接手过一个几万行的 Python 项目，完全没接触过。我把 Claude Code 开在项目目录里，直接问「这个项目架构是什么样，数据怎么流动的」。它花了大概两分钟，通读了整个代码库，然后给了我一个特别清晰的结构梳理，连每个模块的职责都标出来了。

坦率的讲，这个活我自己来干，至少得半天。

第二个，修 bug。这是我最喜欢的用法。以前遇到一个报错，得自己看堆栈、找源码、定位问题、想方案、改代码、测试验证。现在直接把报错信息扔给 Claude Code，告诉它怎么复现。它会自己去找出问题的代码，分析原因，给你一个修复方案，你确认之后它直接改。整个流程可能就几分钟。

第三个，也是最被低估的用法，自动化。

Claude Code 有个特别 unix 哲学的设计，就是你可以在命令行里 pipe 数据给它。比如你可以在 CI 流水线里嵌入一条指令，让它自动检查代码里有没有新增的文本字符串，有的话自动翻译成法语然后提一个 PR。还有些团队配了 hooks，每次 Claude Code 改完代码之后自动跑一遍格式化和测试，相当于给 AI 也加了一道质量门。

这种玩法说实话我一开始也没想到。

不过我得承认，Claude Code 不是万能的，初期上手确实有一点门槛。

装好之后，最重要的一件事，是写一个 CLAUDE.md 文件。这个文件就放在项目根目录，相当于你给 Claude Code 的「入职手册」。你可以告诉它这个项目的技术栈是什么、代码风格偏好是什么、常用的构建和测试命令是什么。有了这个文件，它的表现好一大截。

这块我当时没太当回事。后来发现不写的话，它每次都要重新摸索你的项目习惯，效率低很多。写好之后，感觉就像它真正变成了项目成员，而不是一个外包临时工。

但有个度的问题。

我看到有些人把 CLAUDE.md 写得特别长，恨不得把整个项目文档塞进去。其实没必要，写太多反而会让关键信息被淹没。最好的做法是只写它必须知道的东西，技术栈、代码规范、常用命令，简洁明了。

然后是 MCP，全称 Model Context Protocol。

这个有点高级，但用好之后真的是质的飞跃。简单说就是让 Claude Code 能连上外部工具和数据源。比如连上你的 PostgreSQL 数据库，它就能直接帮你查表结构、分析数据。连上 Jira，它能帮你更新任务状态。连上 Google Drive，它就能读你的设计文档。

我自己的配置是连了数据库和一个内部文档系统，效果非常明显。以前它只能看代码，现在它连业务背景和设计意图都能一起理解了。

还有几个我个人觉得特别实用但很多人不知道的功能。

一个叫自定义斜杠命令。你在项目的「.claude/commands」目录下放一个 markdown 文件，比如「review.md」，里面写好你想要 Claude Code 做的事。之后你在终端里敲对应的命令，它就自动执行那一套流程。相当于你自己造了一个专属小工具。

另一个叫 worktree 并行。如果你同时有好几个任务要搞，Claude Code 可以在不同的 git worktree 里同时跑，互不干扰。我在一个 worktree 里让它改 bug，切到另一个让它加新功能，两边同时推进。

再说一个很多人忽略但我觉得特别重要的点。

动手写代码之前，先让它做规划。

Claude Code 有个 Planning Mode，你让它先出方案、列步骤，你确认之后再动手。听起来多了一步，但这一步能省掉大量的返工。因为 AI 跟人一样，想清楚再动手和直接上手干，出来的东西质量天差地别。

我看到有人在社区里分享说，「vibe coding」那种凭感觉让 AI 写代码的方式，拿来做个一次性 demo 还行，但真正要上生产环境，不做规划就直接开干，后期维护成本会高到让人崩溃。

我自己深有体会。刚开始用的时候就是想到哪说到哪，让它改这改那，改着改着就乱了。后来养成先规划的习惯之后，效率和代码质量都上了一个台阶。

说了这么多，我想回到一个更本质的问题。

为什么 Claude Code 让我这么兴奋？

不是因为它能写代码。写代码的工具太多了。让我兴奋的是，它改变了我和代码之间的关系。

以前写代码是一个「我输出、机器执行」的过程。我用键盘敲，电脑跑。现在的感觉更像是在协作。我定方向、定标准、做决策，它负责执行、验证、迭代。我变成了一个更像产品经理和技术架构师的角色。

这让我想起一件很有意思的事。

1880 年代，电力开始在美国工厂普及。很多老板花大价钱买了发电机，装了电动机。但是装完之后发现，生产效率并没有明显提升。

因为他们只是把蒸汽机换成了电动机，整个工厂的布局、流程、管理方式完全没变。

真正吃到电力红利的那波人，是那些重新设计了整个生产流程的人。

AI 编程也是一样。你只是把手写代码换成了让 AI 写代码，但工作方式没有变，那效果就很有限。真正省下时间的人，是那些重新想清楚了「人和 AI 各自该干什么」的人。

Claude Code 给了一个很好的起点。它不试图替代你，它坐在你旁边，干那些重复的、繁琐的、但不得不干的事。让你把精力放在真正需要人来做的事情上，想清楚做什么，而不是怎么做。

如果你还没试过，我的建议是，随便找一个你正在做的小项目，花一个下午，从 0 开始把它跑起来。不要追求完美，先感受一下那种「旁边坐了个靠谱同事」的感觉。

一开始可能有点笨拙，花的时间比你自己来还慢。

但坚持一两周之后，你会发现省下来的时间越来越多。

不是那种「节省了 20%」的感觉。是那种「等等，这个东西我以前要搞一天的，怎么半小时就搞完了」的感觉。

怎么说呢，可能夸张了。也可能没有。

反正你试试就知道了。
